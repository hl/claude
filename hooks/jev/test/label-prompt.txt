The prompt given to the one blind labelling agent (model opus) for the real routing
eval set, verbatim. label-batches.sh writes the batch files it reads; run the agent,
then `label-batches.sh --merge`. Labels reproduce only up to that agent's judgement.
Known bias: 30% of the briefs carry a line naming the tier their author chose
("Model: haiku — ..."), and the labeller agreed with that line 93% of the time
(70% agreement with the tier that ran where no such line exists); route.sh strips
these lines, the labeller saw them. See README "Routing".

-----

You are labelling a routing eval set. For each subagent task, decide which Claude model tier is correct for it: haiku, sonnet or opus. This is local, private data from the user's own transcripts; never copy it anywhere except the label files below, never commit anything, never edit anything else.

Input: 12 batch files, ~/.claude/jev/eval/batches/batch-01.md .. batch-12.md (about 40 tasks each, ~70 KB each). Each task starts with a line `=== TASK <id>` followed by its description, subagent_type and prompt (long prompts are cut in the middle; the cut is marked).

Output: for each batch-NN.md write ~/.claude/jev/eval/labels/batch-NN.jsonl, one JSON object per task, in the same order, exactly: {"id":"<id>","tier":"haiku|sonnet|opus","reason":"<one line, <= 120 chars>"}. Every task in the batch must have exactly one line. Write each batch's file as soon as you finish that batch (so progress survives), then move on. If a label file for a batch already exists and has a line for every task, skip that batch. Validate each file with `jq -c . file >/dev/null` after writing.

Rules — label blind and on the merits:
- Do NOT open ~/.claude/jev/eval/harvest.jsonl, sample.jsonl, labelled.jsonl or any transcript: they contain the model that was actually used and would bias you. Do not run route.sh or any Jev tool. Judge only from the task text.
- The correct tier is the lightest one that gets the task right in one pass. The user's loss function: cost is not a concern, wasted tokens are. A retry or escalation round costs more than starting one tier up, so when you are genuinely in doubt between two tiers, pick the higher one. But do not inflate: a mechanical poll or a typo fix is haiku even if it sits in an important project.
- Tier definitions (verbatim from the orchestrator's rulebook):
  - haiku: mechanical, well-specified, low-risk work. Polling CI/PR status on your behalf, fetching or extracting log output (diagnosis goes to sonnet or higher), simple lookups, trivial edits (typos, version bumps, renames with exact instructions).
  - sonnet: routine, well-scoped implementation and fixes with clear acceptance criteria, straightforward investigation, addressing simple PR comments.
  - opus: ambiguous or cross-cutting changes, design decisions, tricky debugging, security-sensitive or high-blast-radius code, first-round reviews of non-trivial diffs, and anything where you can't confidently predict sonnet will succeed.
  - Also: CI or comment fixes that need judgement go to sonnet or higher. For non-trivial changes a reviewer is at least the implementer's tier.
- Judge the task as briefed (what the prompt asks the subagent to do), assuming the subagent has the repo and tools. Long, detailed prompts are not automatically opus: a long but fully specified mechanical procedure can be haiku/sonnet; a short "figure out why X happens and design a fix" is opus.
- The reason names the deciding property (e.g. "poll CI until done, no judgement", "clear spec, one module, tests given", "first-round review of a multi-file auth diff").

Work batch by batch. Read each batch file in chunks if needed. When all 12 are done, run: `for f in ~/.claude/jev/eval/labels/batch-*.jsonl; do echo "$f $(wc -l < $f)"; done` and `cat ~/.claude/jev/eval/labels/batch-*.jsonl | jq -s 'group_by(.tier) | map({(.[0].tier): length}) | add'`, and report those two outputs plus any task you found impossible to judge (id + why). Keep your final report short.
